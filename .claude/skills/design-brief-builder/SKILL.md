# Skill: design-brief-builder

## 触发条件

以下任一情况激活：
- 工作流节点 0-B2（PRD 创建后，有 UI 项目）
- 用户明确说「做设计规范」「生成 Design Brief」

**不触发于**：纯 CLI/API 项目（无 UI 界面）

## 执行流程

### 前置检查

读取 PRD.md，判断项目是否有 UI 界面：
- 有 UI → 继续
- 无 UI → 告知用户跳过：`本项目为 API/CLI 类型，设计规范不适用，已跳过 design-brief-builder`

### 多轮追问（每次一问，不批量提问）

按以下顺序追问，每问等待用户回答后再问下一个：

1. **产品定位**  
   `这款产品的风格更接近哪款产品？(如 Notion / Linear / Figma / VSCode / 其他)`

2. **配色方案**  
   `主色调选择？(深色模式 / 浅色模式 / 跟随系统)`

3. **主题色/点缀色**  
   `产品的性格色彩？(高饱和强调色如蓝/绿/橙 / 中性低调灰阶 / 品牌色: ___ )`

4. **内容结构感**  
   `文档/内容的结构偏好？(沉浸式纯文本如 Markdown 编辑器 / 结构化区块如 Notion / 混合)`

5. **交互元素风格**  
   `按钮/控件风格？(实心大按钮 / 幽灵按钮透明底 / 图标按钮极简)`

6. **动效偏好**  
   `界面动效？(无动效 / 微动效过渡 / 丰富动效)`

7. **参考产品名称**（可选）  
   `产品名称是什么？(用于文档抬头，可跳过)`

### 生成 Design-Brief.md

根据 PRD.md + 用户回答，生成规范文档，写入项目根目录 `Design-Brief.md`：

```markdown
# Design Brief: {产品名称}

> 基于 PRD.md 和设计追问生成。开发时与设计图共同作为 UI 实现的最高优先级参考。

## 产品定位与风格方向

{参考产品} + {一句话描述核心设计哲学}

## 配色系统

| 角色 | 颜色定义 |
|------|---------|
| 背景主色 | {hex/描述} |
| 表面色 | {hex/描述} |
| 文字主色 | {hex/描述} |
| 文字次色 | {hex/描述} |
| 点缀色 | {hex/描述} |
| 边框色 | {hex/描述} |

## 布局规范

{三栏/双栏/单栏，具体尺寸和比例}

## 交互元素规范

- **按钮**: {样式描述}
- **输入框**: {样式描述}
- **导航**: {样式描述}
- **卡片/面板**: {样式描述}

## 排版规范

- **字体**: {系统字体栈}
- **标题层级**: {大小和字重}
- **行高/间距**: {规范值}

## 动效规范

{无/微动效/丰富动效 + 具体时长和缓动函数}

## 设计原则

1. {原则1: 如"界面尽量隐形，内容是主角"}
2. {原则2}
3. {原则3}
```


## 语言与输出规范

- **交互语言**：检测用户消息使用语言，以相同语言回复（中文用户 → 全程中文交互；英文用户 → 英文交互）
- **持久化文档**（写入文件的内容）采用 **zh/en 双语**：
  - 标题行：`## 配色系统 / Color System`
  - 表格表头：`| 角色 / Role | 说明 / Description |`
  - 描述段落：中文正文 + 英文括号辅助 `（English clarification）`
  - 代码、路径、命令：保持英文，不翻译
- **状态/提示消息**（如 ✅ ⚠️ 前缀行）：使用检测到的用户语言，无需双语

> AICAM 整体文档（CLAUDE.md / WORKFLOW.md / README）为三语版本（zh/en/zh-tw）。  
> 新 Skill 产出的 .md 文档遵循 **zh/en 双语**规范；README 同步由 Phase F-2a/b/c 完成。
